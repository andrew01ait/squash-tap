# Architecture — 0.13.0

## Match model and storage

- `ScoreState`: Android-independent PAR-11 game, win by two, rally history, Undo and validated `1|` serialization, plus score-only `2|me|opponent` completed sets.
- `MatchState`: best-of-three/five progression; guarded in-place format changes preserve the match ID, all set/rally data and Undo. Finished matches cannot change format, and shortening is rejected if it would immediately finish the match. Normal M1 score/match encoding is unchanged; retirement-only states use M2, and states containing entered sets use M3; won sets wait for Next; Undo can cross an empty next-set boundary. Versioned `M1|` serialization retains each set’s rally history.
- `MatchResult`: immutable completed-match summary with local ISO completion date, daily number, match format, set scores, an optional retired player, UTC epoch-millisecond start/finish values and the captured clock timezone. Start time replaces Match N as the heading; the daily match reference remains secondary. Validates plausible winning scores and progression.
- `MatchBook`: current match, saved results, persistent daily counters and a deletion marker for the current result. The complete unit is stored atomically in `SharedPreferences("squash")`, key `match_book`, schema `B4:` followed by Base64 binary data, with backward reading of B1/B2/B3. Saving the last point also saves its result. Undo removes a stale current result; re-completion reuses its original reference. Deletion never reuses numbers or revives a deleted result.

v0.1/v0.2’s `score` is migrated once into the first set of a BO3 match and left intact for recovery. Malformed new data is retained as `match_book_recovery` before fallback. On B1/B2/B3 → B4 conversion, MainActivity preserves each original string once under `match_book_v1_backup`, `match_book_v2_backup` or `match_book_v3_backup` before persisting the upgraded book. Existing untimed results stay untimed; an already-active legacy match remains start-unknown while its future finish can be recorded, unless the user explicitly saves a manual set and uses that save time as a missing start. Synchronous preference commits precede result confirmation; failures show a retry message. The history is capped at 10,000 results, with bounded decoding. If full, the completed scoreboard is kept and the user is asked to delete old results before explicitly saving it through Current match. Date counters are retained after deletion.

## Match timing

MatchBook has an injectable java.time.Clock. The production scoring path takes a single instant per accepted rally, derives the completion day from the same clock/zone, starts timing on the first point and freezes finish time at the match-winning point. Setup time is excluded; breaks/pauses and time spent outside the app are included. No periodic timer or wake lock is added.

B2 adds current start/finish/zone/eligibility fields and per-result timestamps. Zero means not started/unknown, never an invented old timestamp. The legacy eligibility marker prevents a mid-match update from pretending that its next point is the original start. A fresh empty B1 match may begin timing on its first point. B1 completed results, score/rally history, counters and deletion markers are retained. Synthetic B1 fixtures are under android/test-fixtures.

Undo clears finish and the stale current result, keeps the original start/reference, and records a new finish at re-completion. New match resets timing; format changes and set transitions retain it. A full history keeps the finish captured at the winning point while the user frees result space. Start-zone display is stable across later timezone changes; UTC subtraction handles midnight/DST. If the watch clock moves backwards, duration is unavailable rather than negative. B2 rejects corrupt timing/zone data and disagreement between current and saved-result timing.

## Watch UI and lifecycle

`MainActivity` owns storage, menus, results/deletion, permissions, updater actions and an AndroidX LifecycleRegistry. `ScoreView` draws the round scoreboard; shared `TouchTargets` reject swipes, multi-touch and long presses as scoring taps. Me is blue, Opponent red. The scoreboard header opens Menu with Current match, Results, Statistics, Opponents and Settings. Current match puts its session action first; Match options contains opponent/format/replacement/retirement. Historical manual capture lives in Results. Root Settings is explicitly grey. Only general controls (version, updates, display/notification and diagnostics) live in Settings.

Saved results use native rounded cards (LinearLayout/TextViews), with blue/red backgrounds and borders according to the winner. List cards open the full result; the detail card includes all set scores. Match actions, including scoreboard Undo/New, use blue button styling and blue disabled states. Each action explicitly chooses MATCH, PERSON, SETTINGS, DELETE or BACK. Match controls are blue, Settings neutral grey with equal RGB channels, delete actions/confirmations red, and Back/Cancel transparent with cyan outlines. Filled controls set their own background tint after creating the drawable, so theme accents cannot recolour them. Style is never inferred from a container tag.

`MatchDisplayPolicy` requires an explicit `active_match_id` equal to the current match ID, an unfinished match and no pause. An unfinished score alone is insufficient. The first accepted scoring tap or Start/Resume activates the session; pause, completion, task removal and new-match setup clear it. Existing installations with no active ID stay idle until Resume for a point-bearing match. Scores/B2 timing are unchanged. Undo to zero during active play retains the session; Undo after completion remains idle until Resume. This prevents opening a draft, old score or result from starting a sticky service.

`AmbientLifecycleObserver` is attached only while the session is ongoing. Removing it delivers the appropriate pause/stop/destroy callbacks to release its wearable controller; resuming creates a new observer. The main Activity's lifecycle still follows Android events. Ambient support enables a black, monochrome score/time display with minute ticks, small positional shifts and low-bit anti-aliasing handling. Ambient input does not score. Keep screen on defaults ON and also requires a resumed scoreboard without panels or ambient. Dialog dismissal restores it only for active play. The QR window's separate keep-awake flag expires after 60 seconds and is cleared immediately on backgrounding.

`MatchSessionService` hosts one silent, low-importance ongoing notification with AndroidX `OngoingActivity`, current score/status, a static monochrome icon and a touch intent back to the single-top activity. This foreground service uses Android 14’s `specialUse` type for the user's scorekeeping session. It independently checks the persisted active ID, pause and completion on every start, including null-intent sticky restarts; invalid/idle state stops immediately with START_NOT_STICKY. Active play persists across ordinary activity pause and can restore after process recreation. Task removal durably clears the session ID and pauses the match. Notification permission is requested only during active play on Android 13+; Settings offers another enable action if needed. No exercise sensors, periodic worker or app-held CPU wake lock are used.

The design follows Android’s [ambient and app visibility guidance](https://developer.android.com/training/wearables/always-on) and [ongoing activity guidance](https://developer.android.com/training/wearables/notifications/ongoing-activity). Actual OnePlus firmware behaviour remains a physical acceptance test.

## Diagnostics

`AppDiagnostics` retains a bounded private lifecycle/session trace and last uncaught Java exception; it delegates to Android’s original crash handler. Recent `ApplicationExitInfo` records distinguish crashes/ANRs, low memory and other system exits when Android supplies them. Reports include current version, device, notification/install permissions, match/session state, power settings, current page and scoreboard-window flag. Activity-pause events retain the page and pre-pause window flag. Numeric package-update exits are labelled App updated, and truncated traces start on a full line. These logs are diagnostic evidence, not a guaranteed record of every firmware action.

`BatterySnapshot` reads BatteryManager capacity/charging status only on explicit session changes and diagnostic export. Unsupported readings are labelled unavailable. Session start/pause/finish/task-removal events include a timestamped snapshot in the existing bounded trace. There is no listener, sampler or timer. These are whole-watch readings, not app-attributed consumption or a battery benchmark.

`DiagnosticTransfer` gzip-compresses a bounded UTF-8 report, Base64URL encodes it and places it after `#d=` on the fixed HTTPS `/diagnostics.html` URL. ZXing draws a watch QR code. The phone page decodes locally with browser DecompressionStream, renders via textContent, bounds input/output, clears the fragment and offers TXT save/share/copy. There are no third-party scripts or automatic report uploads. The full watch report and compact QR report have different trace/stack limits; neither contains match rally history or a unique device identifier.

## Updates and hosting

`UpdatePolicy` treats release properties as untrusted: exact package/schema/version/SDK, bounded size, SHA-256 syntax and fixed-host HTTPS without credentials/nonstandard ports. `VerifiedDownload` enforces streaming size/hash. `UpdateClient` rejects redirects, stages the APK, checks package identity and installed signer, then uses PackageInstaller. `InstallReceiver` handles result/pending confirmation. Both checks and downloads require a Settings action. There is no launch check, scheduled job or background update polling. The executor starts no thread until work is submitted.

The public Site presents a concise feature overview and phone installation/update guidance for external users, with immutable versioned APKs from v0.3.0 onward, checksums, source ZIP, notices, phone diagnostics decoder and `release.properties`. `scripts/release_retention.py` enforces the minimum version code of 3, retires earlier binaries/signature sidecars and refreshes the release inventory/checksums without changing the live update feed. Earlier experiments remain documented as historical evidence. Audience stays public at the user’s explicit request. The only hosted state is short-lived encrypted transfer state; no permanent score database, telemetry or server-side diagnostic receiver exists.

## Opponent metadata and CSV

OpponentDirectory stores O1 metadata under opponent_book alongside B4 match_book (B1/B2/B3 migration retained) in a single preference commit. It holds stable person IDs, NFC-normalized names (60 code points), an archived flag and match-ID assignments. Empty old metadata migrates to an empty directory; corrupt values are copied to opponent_book_recovery. Names are never inferred for older matches. Archived identities remain on history; renames resolve through their ID. Scoring, Undo, timing, daily counters and deletion markers stay in MatchBook. ResultFilter composes person/unnamed and inclusive date bounds and sorts by recorded date/start/reference.

MatchCsv implements bounded RFC-4180 parsing and spreadsheet-safe reversible text escaping. It validates every final set, match progression, timestamp/zone, duration and summary before planning a merge on cloned books. An existing identical match ID is a duplicate even if a local reference was adjusted previously. Foreign reference numbers cannot advance/exhaust the local daily counter. A differing existing ID or any current-match ID is a conflict and is skipped. MatchBook.importResult preserves the current scoreboard and allocates references beyond the date counter for each newly imported result. No existing result is overwritten. Preview checks the directory/current-match fingerprint; confirmation checks the complete local books again before an atomic commit.

## Encrypted temporary relay

TransferClient uses explicit, bounded, fixed-origin HTTPS requests with redirects disabled and 12/20-second connection/read timeouts. The activity retains an in-memory session ID, AES key, separate owner/guest capabilities and expiry. No key/capability is persisted, logged or added to diagnostics. TransferCrypto and public/interchange.mjs share gzip + AES-256-GCM with 12-byte random IVs, 128-bit authentication tags and AAD `squashtap-transfer-v1|sessionId|direction`. Context binding rejects cross-session or cross-direction replay. Browser/native golden vectors are checked both ways. Expanded input is capped at 4 MiB and compressed input at 1 MiB.

The watch creates one outgoing snapshot of selected CSV results, the complete opponent catalog, current assignment and a baseline fingerprint. Its short QR is /transfer.html#id=…&p=…&k=…. The page removes the fragment immediately, decrypts locally and renders text/inputs without HTML interpolation. Download/filter actions stay in the browser. Send changes seals a complete proposed catalog/current assignment and optional CSV; one incoming submission is allowed. Receive and Apply are separate watch actions. A stale catalog/current match is rejected; score changes before the receive preview are retained, and any local change after the preview invalidates confirmation.

worker/relay.mjs intercepts only /api/transfer in the Vinext Worker. D1 stores session IDs, hashed owner/guest capabilities, expiry and pending state plus short-lived hashed-IP rate buckets. R2 stores opaque ciphertext under expiry/session/direction keys. Owner/guest roles limit reads/writes/ending; tokens go in Authorization headers after creation, not URL paths. Requests are size-bounded, same-origin checked, no-store and without CORS grants. Creation is bounded to 12 attempts per ten-minute IP bucket and 250 simultaneous sessions; insertion enforces the global limit atomically. Names and plaintext CSV never enter the relay database or logs.

Access expires at ten minutes. Ending or successful confirmation deletes D1/R2 data immediately when the request succeeds. Expired objects are removed in bounded oldest-first batches on later API traffic and expired metadata is deleted then; there is no separate cron/physical-erasure deadline. Failed or orphaned writes are handled or collected by their expiry prefix. Hosting-provider backups are outside this application-level cleanup guarantee. No watch timer, background transfer service, repeated receive request or telemetry is introduced.

Canonical release assets now live in public/; the supported Vinext build produces dist/client and dist/server with Sites provisioning D1 DB and R2 BUCKET. The original public URLs/package/signer remain stable. The diagnostic decoder is unchanged. A synthetic-watch preview helper is guarded by import.meta.env.DEV and must be absent from the production bundle.

## Optional new-match opponent — v0.9

MainActivity holds newMatchOpponent only as an in-memory setup draft. Entering NEW resets it to no name; opening/closing the picker retains the staged choice. A null match ID with filtering=false identifies this setup picker and never calls OpponentDirectory.assign on the current match. Adding a name saves the catalog and returns its ID through a callback; it does not assign the old match. Setup omits the phone-current-match shortcut to avoid changing the old match while preparing a new one; names can still be managed through the main phone entry.

Format selection captures the staged ID for the existing replacement confirmation. startMatch validates that the optional ID is selectable and builds cloned MatchBook/OpponentDirectory objects before switching the current books. Only the confirmed new UUID receives the selected opponent. B2 and O1 schemas, prior assignments, results, timing and Undo are unchanged. The normal new-match idle policy still applies. PERSON is an explicit purple role with a person vector icon, left-aligned text and its own pressed/disabled colours; it is used for names and person-selection fields rather than inferred from parent panels.

## Compact timing and derived statistics — v0.10

MatchResult.timingText formats the recorded start date once and uses HH:mm Start/End values in the stored zone. A finish on another local date includes that end date. Finish-only and untimed legacy records keep missing times explicit. Detailed result cards omit the redundant date/title/reference-date text; history titles still identify the start date/time. Full timestamps, duration calculations, CSV and persisted formats are unchanged.

MatchStatistics is a pure, read-only aggregate over MatchBook.newestFirst(). It derives Me match wins/losses, sets (games) won/lost, each side’s points, totals, signed balances and win rate using long counters. No aggregate is persisted. The overall Statistics page deliberately ignores result filters, reads all saved completed results on each opening and starts no task, transfer, service or screen flag. Existing import/delete/Undo semantics determine which results count; B2/O1 and atomic persistence remain unchanged.

## Retirement and B3 — v0.11

B3 is the current write format. It extends each completed MatchResult with retiredPlayer (-1 normal, 0 Me, 1 Opponent), retains the B2 header/timing/counters/tombstone structure and reads both B1 and B2. onCreate keeps a B2 recovery backup before writing B3. Normal current MatchState serialization remains M1; a retired current state uses M2 and records only the retired player alongside the real rally histories. Validation rejects retirement after a natural match win, invalid participants, scores beyond a set’s winning point and an unfinished set before another set. No synthetic set win or rally is stored.

MatchState.winner uses the opposite player for retirement. MatchResult counts only genuinely completed sets; statistics includes a retirement in match W/L, actual finished sets and every played point. Confirmation records finish with the existing clock/zone policy. Undo clears retirement first, preserving all rallies, then MatchBook removes the result and retains its daily reference and deletion marker. Re-completion reuses the reference. Existing session policy stops power retention because a retired match is complete.

CSV headers/rows remain schema 1 when no retirement is exported. Schema 2 appends retired_player (empty, me or opponent) and supports a final partial set or a between-set retirement. Native/browser validation, winner rules and totals agree; conflicts include a different retirement outcome for the same ID. The browser gates retired imports for older watch snapshots. O1 and the relay schema/protocol remain unchanged.

## Explicit phone assignment and private browsing — v0.11

Catalog additions/restorations do not mutate the selected match opponent. Phone payloads preserve the snapshot’s existing opponent unless the separate checkbox is enabled. New native previews apply a match reassignment only for the literal boolean changeCurrentOpponent=true and highlight it before commit; older accidental selection payloads are ignored for assignment while catalog edits still merge. Renaming an existing identity remains a deliberate linked-name edit.

Browse on phone exports the entire completed history through TransferClient’s existing encrypted snapshot. Optional totalResults and currentMatchComplete metadata clarify scope and editing target. Phone rendering/filtering/pagination/statistics runs in memory. The Statistics tab always uses all rows in the snapshot, groups head-to-head totals by stable opponent ID, includes unnamed history and provides recent W/L links into full results. No additional API calls, accounts, plaintext server state or persistence are introduced. Encryption keys remain in memory/QR fragments and expiry destroys the page’s data views.

## Entered set totals and independent manual results — v0.12

B4 is the current write format, with the same book header/result layout as B3 and guarded support for score-only current sets. ScoreState’s normal 1|rallies encoding is unchanged. 2|me|opponent contains a validated final PAR-11 set total and explicitly lacks rally order. It cannot accept a point or undo an invented rally; reset returns to normal tracking. MatchState uses M3 when any set is entered, recording the existing retired-player flag as well. M1/M2 remain normal/retired live encodings. Older labelled formats reject entered sets instead of silently misreading them.

MatchState.enterCompletedSet replaces an unfinished current set or appends after a completed set, preserving earlier sets. MatchBook confirmation captures an optimistic book fingerprint, keeps any existing start timing and, from v0.12.1, records a single current clock instant/zone when saving a set if the start is absent (including a previously untimed v0.12 current match). This accepted-entry timestamp also determines the completion day if needed. A manually submitted final set’s actual finish remains unknown. Later genuine live scoring may record its own finish. Undo identifies a summary (including across an empty next set) and removes that whole entered set after a UI confirmation. Natural rally Undo and retirement-first Undo keep their semantics, counters and deletion markers.

ManualMatchEntry is an in-memory independent completed-match draft with atomic prefix validation, format changes, set edits/removal, optional stable opponent ID and bounded date choice. Save clones the current book/directory, allocates an independent UUID/reference and commits both atomically without replacing current match/session data. A successful save invalidates the draft to prevent double submissions. Histories contain the same validated MatchResult summaries/CSV as before, with unknown timing represented by zero/empty fields.

ManualEntryUi provides native blue/red score cards, touch-sized controls and NumberPicker wheels with FOCUS_BLOCK_DESCENDANTS. Manual panels request SOFT_INPUT_STATE_ALWAYS_HIDDEN. Winner plus losing-score selection derives a valid win-by-two total; score presets and +/− are alternative touch paths. Date uses the same keyboard-blocked wheels, with leap-day clamping and future-date rejection. Saved-person picking is separate and optional, with no keyboard editor on this route. No new dependency, sensor, network call, background job or wake lock is introduced.

### Manual-set start fallback — v0.12.1

MatchBook.enterCompletedSet sets a missing start only after accepting valid set totals, with timingEligible restored for B4 consistency. Confirmation, cancellation and decoding never stamp it. Repeated entries, Undo and later live points keep the first start/zone. No new persistence format, timer, network call or active-session transition is introduced. Independent ManualMatchEntry historical results keep zero start/finish fields.

## Contextual navigation — v0.13

MainActivity retains explicit caller callbacks for setup, results, opponent pickers and phone actions. Each panel binds its one outlined Back/Cancel callback to the button, dialog cancel/system Back and AndroidX SwipeDismissFrameLayout dismissal. Existing wear:1.3.0 supplies this native wrapper; setSwipeable(true) is explicit. Internal dialog replacement/dismissal does not fire a user Back route. A header Scoreboard shortcut is independent of Back and leaves session state untouched.

Result/opponent lists use keyed ScrollViews. A bounded 64-entry in-memory map retains scroll positions by page/filter key; returning to a detail caller preserves its page/filter and restores scroll. No UI navigation state is written into match data. New-match BO3/BO5 and person choice stay staged until Create match; replacement is separately confirmed. M1/M2/M3, B4/O1 and timing are unchanged.

Phone actions capture their caller, desired view and export scope. A whitelisted view parameter in the QR fragment selects Results, Opponents or Import locally after decryption and fragment removal. It changes neither authorization nor snapshot contents. Existing full/subset transfer guards remain. Creation/receive completion only opens a panel if its waiting dialog is still current, avoiding late redirects over scoring. No polling, permanent link storage or new runtime dependency is added.

## Public shell and per-transfer access

The download/phone HTML shells are public. Anonymous transfer.html has a hidden empty workspace and makes no session request until a valid QR fragment supplies a session ID, guest capability and encryption key. The relay checks tokens against the requested session row; no list endpoint is exposed. Independent sessions cannot read/write/delete one another, and AES-GCM binds ciphertext to its session/direction. This is secret-link access, not identity authentication: possession of a complete active link grants phone access. The landing page links only to the current APK and a local privacy explanation; retained binaries/metadata are untouched.
